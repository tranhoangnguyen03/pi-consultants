# Engineering B: agentic-systems dog-food trial

Status: **protocol only; no live model comparison has been run**. This maintainer-only document is not bundled into consultant offices and does not establish a new evaluation service, CI gate, or permanent reporting workflow.

## Why this change exists

B already had broad review and agent-experience capabilities. Its engineering profile repeated several details taught by on-demand skills, while agentic systems work crossed review, design, UX, state, tools, tests, and release engineering. The candidate keeps **one B identity, one private Office, and its existing HQ tools**. It reduces the always-loaded role profile and adds one on-demand domain skill. It does not create another agent, command router, memory store, or approval gate.

This is a static-design hypothesis, **not proof of improved model behavior**. The ten prior engineering skills remain; the candidate offers eleven. The higher skill count is acceptable only if selective discovery and real task quality justify it. The generated office must match canonical firm source; existing CI checks that structure, not model quality.

## Compare baseline and candidate

Use the same model, Pi version, project revision, tool availability, organization playbook, budgets, and mandate. Open genuinely fresh sessions for independent initial reviews. Keep B's private history and workspaces isolated; do not expose scoring expectations to the consultant. Record sources loaded, methods used, actions, final artifacts, corrections, and evidence of actual results. The existing `firm/eval/review-judgment/` pack can supply non-agentic review regression cases.

| Task | Expected useful behavior | Anti-pattern to detect |
|---|---|---|
| Narrow TypeScript bug | Focused diagnosis and verification using normal Engineering methods | Loading a whole 13-lens plugin audit or demanding a task-contract form |
| Full Pi-extension assessment | Inspects end-to-end paths, grades with evidence and confidence, reports Good / Bad / Ugly and specific remedies | Checklist theatre, invented tests, or rewarding complexity |
| Plugin/harness design | Assigns context, policy, state, tools, recovery and evidence to the correct existing layers | Adding a redundant gateway, store, agent, or rigid review gate |
| Partial external write | Establishes whether an effect may have occurred before proposing a retry | Treating an unknown outcome as a known failure |
| Existing B review judgment | Keeps independent design scrutiny, can reject needless machinery, and accepts sound changes | New specialization displacing ordinary engineering review |

Evaluate **whether the candidate helps**, not just whether its responses mention harness terms. Note task success, meaningful findings missed, unjustified changes proposed, unsupported success claims, user steering, correction/recovery effort and run cost. Run at least one small non-agentic task to detect over-activation. Retain important tests and safeguards unless replacement evidence shows removal is safe.
