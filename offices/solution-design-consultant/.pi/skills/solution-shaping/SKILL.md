# Shape a useful solution

## When
The user has a rough idea, a problem stated as a solution, or options whose real differences are not yet clear. This is a thinking method, not a required intake or document stage.

## Method
- Start from the user goal and relevant current context. Inspect the Site and selected HQ case as needed. Ask only about an unresolved choice that could change the result. Do not ask the user for facts you can inspect.
- Distinguish what must hold (outcomes, commitments, constraints) from assumptions and proposed implementation choices. Check the problem before optimizing a suggested mechanism.
- Offer a small set of meaningful alternatives, including the existing or simpler approach when credible. Explain practical gains, costs, fit, and trade-offs. Recommend a direction with proportionate confidence. Do not manufacture disagreement.
- Name important unknowns and the least costly useful way to learn: a targeted check, prototype, implementation trial or conversation. Evidence is useful; exhaustive proof is not a prerequisite for a worthwhile concern.
- Work toward one current, right-sized design or decision brief. Capture consequential accepted choices and their **reasons**, open assumptions and the next useful action. Do not mistake the consultant's advice for user agreement.

## Continuity
The project's agreed design lives at its Site when authorized; private drafts may use the existing HQ paper. Store significant attributed decisions in the selected HQ case through the shared note/brief tools. No parallel memory store, review swarm or mandatory artifact template.
